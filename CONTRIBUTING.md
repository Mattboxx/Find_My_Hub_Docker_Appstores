# Contributing to the Docker catalog

[Project overview](README.md) · [Documentation](docs/README.md)

Use `main` as the integration branch. Create one short-lived topic branch per
change (`docs/<topic>`, `fix/<topic>` or `chore/<topic>`), submit a pull request,
and delete it after merge. Keep branches belonging to open PRs. The `gh-pages`
branch is generated by publication; do not use it for manual development.

The recommended new installation is the two-container All-in-One recipe.
The root `compose.yaml` and current native-store adapters retain the legacy
four-container modular layout for existing installations. A documentation or
branch cleanup does not migrate those installations.

Keep store/app IDs, data paths, subscriptions and existing release tags stable.
Use immutable version tags for releases rather than retaining completed release
branches. Never force-update `catalog-VERSION` or publish private application
source, credentials, tracker identities or runtime data.

Before merge, validate JSON, Compose variants and the generated ZimaOS catalog
with the repository CI. Review documentation links and rendered screenshots.
Only reviewed public guides, synthetic assets and installation metadata belong
in this repository; the private application repository is maintained separately.
